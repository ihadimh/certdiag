# Windows 提示"签名无效"，可能根本不是签名的问题

> 一次真实的排查记录：重装、换安装包、关杀软都试过，最后发现是 OCSP 连不上。

几个月前装 Cisco Packet Tracer，打开就是一句：

```
无法验证此文件的签名。签名无效或已损坏。
```

文件是 `qsvg.dll`。

我当时的反应和大多数人一样：安装包坏了。重装。还报错。换一个下载源。还报错。关杀软、加白名单、以管理员身份运行……全部无效。

折腾了两小时后我做了件本该更早做的事：**去看系统到底在说什么**。

结果发现，证书链完整、文件哈希完全匹配、签名者证书也没问题。唯一异常是一项：

```
吊销查询：5/7 个地址可达
  http://ocsp.digicert.com → 连接被重置
```

**文件是好的。是我连不上发证机构。**

---

## 一、一句话的报错，背后有四种完全不同的原因

Windows 那句"签名无效或已损坏"是个筐，什么都能往里装。至少要分成四类，而且**处置方式相反**：

| 现象 | 你以为是 | 实际可能是 | 正确做法 |
|---|---|---|---|
| `OfflineRevocation` / "吊销状态未知" | 证书坏了 | 网络不通、代理拦截、OCSP 被墙 | 换网络或配代理，**别删证书** |
| `NotSigned` / "无法验证" | 文件被篡改 | 可能只是**目录签名**（签名不在文件里） | 查 `.cat`，**别重装** |
| 签名者证书已过期 | 签名失效 | 有时间戳则**仍然有效** | 验时间戳，**别重签** |
| `NotTrusted` | 根证书有毒 | 缺中间证书，或根未部署 | 装中间证书 |

我踩的是第一类：问题不在证书，在连接。

## 二、`cmd.exe` 其实没有签名

打开文件属性 → 数字签名，`C:\Windows\System32\cmd.exe` 是空的。但系统判定它有效。

因为它用的是**目录签名**：签名不在文件里，而是把所有文件的哈希收进一个 `.cat` 文件，对 `.cat` 统一签名。

```
PE 安全目录：RVA=0x0  Size=0     ← 文件里确实没有签名
Get-AuthenticodeSignature：Valid  ← 系统仍然判定有效
```

这就引出一个坑：**两个 Windows API 的说法会不一样**。

| API | 能看到 | 看不到 |
|---|---|---|
| `Get-AuthenticodeSignature` | 嵌入签名 + **目录签名回退** | 不告诉你具体错误码 |
| `WinVerifyTrust` | **精确 HRESULT** | 只看文件自身，**不查目录** |

对同一个 `cmd.exe`：

```
PowerShell  : Valid
WinVerifyTrust: 0x800B0100 TRUST_E_NOSIGNATURE
```

**这不是矛盾，是视野不同。** 如果只看 WinVerifyTrust，你会以为系统组件是未签名的 —— 然后开始怀疑系统被黑了。

## 三、证书过期了，签名可能仍然有效

`git.exe` 的签名证书有效期到 2024-02-01，早过期了。但系统说它有效。

因为签名带**时间戳**：它证明"这个签名是在 2024 年 1 月做的"，而那一刻证书还有效。评估签名有效性要看**签名时刻**，不是今天。

但光看到"有时间戳"还不够 —— 时间戳本身也得是真的。可以把签名 blob 解开，找到里面的时间戳令牌（PKCS#7 里一个未认证属性），把它当成独立的 SignedCms 再验一次：

```
签名者：CN=Johannes Schindelin
未认证属性：1.3.6.1.4.1.311.3.3.1     ← 时间戳令牌
令牌验签：通过
TSA：CN=Microsoft Public RSA Time Stamping Authority
```

验签通过，才能说"这个时间点是某个 TSA 签发的且未被篡改"。否则只算"存在一个时间戳"。

## 四、最容易搞错的：把"查不到"当成"有问题"

回到开头那次事故。

系统的报错是 `OfflineRevocation` —— 字面意思是"吊销查询离线"。看起来和"证书无效"几乎一样。如果我当时信了，接下来就是删证书、重装系统、甚至去改信任设置。

**但它的真实含义只是：我没能问到发证机构，这个证书有没有被吊销。**

"查不到"和"有问题"是两件完全不同的事。我后来把它总结成一条规则：

> **unknown ≠ invalid**

这条规则现在写进了工具的默认行为里：

```bash
# 默认：只有确认无效才算失败
python -m certdiag "D:\release" --fail-on invalid     # 退出码 0/1

# 更严格：连"无法判定"也算失败
python -m certdiag "D:\release" --fail-on unknown     # 退出码 0/1/2
```

默认值就是"不知道不等于有问题"。如果工具的作者都不这么想，用户就更不会。

## 五、想知道自己的文件到底怎么了，五个命令

不用装任何东西，PowerShell 就够：

```powershell
# 1. 系统怎么看（含目录签名回退）
Get-AuthenticodeSignature .\app.exe | Format-List Status, StatusMessage, SignerCertificate

# 2. 精确错误码（只看嵌入式签名）
#    0x800B0100=无签名  0x800B010D=吊销离线  0x80096010=哈希不符
certutil -verify -urlfetch .\app.exe

# 3. 是否有目录签名覆盖
sigcheck -a .\app.exe     # Sysinternals，看 Catalog 字段

# 4. 证书链逐跳看
certutil -dump .\app.exe | findstr /i "Issuer Subject"

# 5. 吊销地址通不通（把证书里的 CRL 地址粘进来）
curl.exe -I http://crl3.digicert.com/xxxx.crl
```

判断顺序建议：

1. 先看是**嵌入签名**还是**目录签名**（决定查哪里）
2. 再看是**证书问题**还是**网络问题**（决定改什么）
3. 最后才看**过期/时间戳**

## 六、三件不要做的事

这三条不是"最佳实践"，是**会让你把好好的系统搞坏**的操作：

1. **不要因为"签名无效"就删证书。** 网络问题不会因为删证书而解决。
2. **不要关闭签名校验、关杀软、加白名单。** 这等于把警报器拆了。
3. **不要把"查不到吊销状态"当成"证书有问题"。** 重装系统解决不了 DNS 问题。

## 七、如果不想记这些

我把这套判断做成了一个工具：**[certdiag](https://github.com/ihadimh/certdiag)**。

- 只读诊断，不改系统
- 零第三方依赖，有 11 MB 的免安装便携版
- 把"证书问题"和"网络问题"分开说清楚

```bash
python -m certdiag "C:\path\to\app.exe"
```

```
文件：app.exe
状态：Valid（签名已通过验证。）
结论：✅ 有效 — 文件自身没有嵌入式签名，有效性来自目录签名（catalog）
分类：catalog_only_trust  置信度：high
目录签名：Microsoft-Windows-Client-Desktop-Required-Package0511~...cat（Valid）
```

它内部只有一条不算高明的原则：**先分清是哪一类问题，再谈结论**。为此它区分了二十几种结论，也明确了三种结果：

| 结论 | 含义 |
|---|---|
| `valid` | 通过 |
| `invalid` | **确定**有问题（哈希不符、根不受信、过期且无时间戳、被吊销） |
| `unknown` | **无法判定**（网络不通、离线、OCSP 不可测） |

第三条最容易被省略，也最重要。

最后一件事是关于吊销的。写这个工具的过程中我才意识到，很多校验工具（包括我第一版）都悄悄跳过了吊销检查，然后在报告里写"签名有效"。

我后来把它改成了显式开关：默认不查，报告里就写「吊销：未检查」；想要结论就加 `--revoke=auto`，它会先探一下地址通不通，通才真的去查，不通就告诉你原因。

**"没查"和"查过、没问题"是两件事**，工具不该替用户把这两件事混成一件。

**下次看到"签名无效"，先问一句：是证书的问题，还是我连不上它？**
