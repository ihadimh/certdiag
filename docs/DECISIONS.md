# 设计决策记录（DECISIONS）

> 用途：**为什么这么做**。代码能说明"怎么做"，说明不了"为什么不做另一种"。
> 改代码前先看这里，能避免把已经否定过的方案再提一遍。

## D1 · `unknown ≠ invalid`，且默认 `--fail-on invalid`

**背景**：qsvg.dll 那次，系统报 `OfflineRevocation`（吊销查不到），看起来像"证书坏了"。
实际只是网络不通。

**决策**：结论分三类 valid / invalid / unknown；默认只有 invalid 让退出码变 1。

**理由**：把"查不到"当"有问题"，会让人删证书、重装系统。宁可漏报也不误报。

**代价**：想拿它当签名门禁的人会失望——所以补了 `--require-signature`（另一个用途）。

## D2 · 只读，不做任何写系统操作

不装证书、不改注册表、不加白名单、不"修复"。

**理由**：诊断工具一旦会写，用户就无法判断"问题是修好了还是被掩盖了"。

## D3 · 目录签名与嵌入签名分开处理

`Get-AuthenticodeSignature` 会回退查目录签名，`WinVerifyTrust` 不会。同一个 cmd.exe，
一个说 Valid，一个说 `TRUST_E_NOSIGNATURE`。

**决策**：两个 API 都取，交叉判断；**目录签名必须校验 `.cat` 自身的签名状态**，
不能"找到 .cat 就算可信"。

**踩过的坑**：最初只看 `catalog.found` 就判 valid，评审指出这是把"找到"当"可信"。

## D4 · 时间戳只验到"令牌签名有效"，置信度 medium

**决策**：只做 `SignedCms.CheckSignature`，不声称"可信时间戳"。

**理由**：完整校验需要 messageImprint 绑定、TSA EKU、TSA 链时效，超出零依赖边界。
**未做的三项写在 README 里**，让用户知道边界在哪。

**踩过的坑**：最初写成 `expired_with_verified_timestamp` + high，评审指出过度自信。

## D5 · `--revoke` 四档，off 为默认

`off / cache / auto / online`。

- `off` 是默认：快，但报告必须写"未检查"
- `auto`：先探地址，可达才联网查（把 probe 从"推断依据"降级为"前置条件"）
- `checked` 由**链的真实结果**决定，不是由"档位≠off"推断

**踩过的坑**：最初三处都 `NoCheck`（链、WinVerifyTrust、只探测网络），
却在报告里写"吊销检查通过"。这是把"没查"说成"查过了"。

## D6 · 证书里的地址不可信，内网默认不探测

证书是文件的一部分，可以被伪造。恶意文件可以写 `http://10.0.0.1/`。

**决策**：解析后判断 IP，内网/回环/链路本地/保留段一律跳过；内网 PKI 需 `--allow-private`。

## D7 · 退出码 0/1/2/3

`0` 全有效 · `1` 有确定无效 · `2` 有无法判定（strict 模式才会返回）· `3` 运行错误。

**理由**：CI 需要能区分"文件有问题"和"工具自己出错"。

## D8 · 零第三方依赖 + 便携包，不做 exe

**理由**：打包成 exe 会是**未签名的可执行文件**，触发 SmartScreen 和杀软误报——
正是这个工具要诊断的那类问题。

**代价**：入口只能是 `.cmd`，所以补了「创建桌面快捷方式.cmd」给图标。

## D9 · 版本号单一来源

`certdiag/__init__.py` 的 `__version__`。报告、构建脚本都引用它，不写死。

**踩过的坑**：报告里曾硬编码 0.1.0 而包是 1.2.0。

## D10 · 规则表与代码同步，由测试保证

`rules.py` 的 24 条规则必须覆盖 `report.py` 里所有分类标签，否则测试失败。

**理由**：新增一个分类却忘了写说明，用户就会看到一个没有解释的结论。
